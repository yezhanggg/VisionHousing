# VisionHousing — working rules for AI coding assistants

Read this before every task.

## What this project is

An open-source, interactive tool that estimates how **state-level housing policy reforms** change **housing production over five years** compared with a no-change baseline. It is built for the Housing Data and Technology Innovation Challenge. It favours transparency, interpretability, honest uncertainty, and practical policy insight over forecasting complexity.

## Who does what

The AI assistant writes all code, tests, configuration, and documentation. Ye Zhang (team lead) directs the work, reviews it, makes the decisions, and makes every commit, push, and submission. **The assistant never commits, pushes, tags, or stashes.**

## Rules

| Rule | Why |
|---|---|
| Explain every module in plain language (docstrings and `docs/modules/`) | The team must be able to explain the code; unexplained code scores lower |
| Write tests for all core analytical logic; tests must pass on a clean checkout | Pass/fail requirement |
| Never commit secrets, keys, tokens, or large datasets | Pass/fail requirement |
| Fetch all data by script from its authoritative source; store none of it in the repository | Pass/fail requirement |
| Use only permissive, OSI-approved dependencies — no GPL, AGPL, LGPL, MPL, EUPL, source-available, non-commercial, or unknown licences | Licensing requirement; `make verify` runs the licence audit |
| Record every AI tool, model, external service, dependency, and dataset in `DISCLOSURES.md` | Disclosure requirement |
| Report results as ranges with sensitivity, never as single-point forecasts | Handbook requirement |
| Prefer simple, transparent methods; any statistical model must be explainable | Transparency is 30% of the score |
| Keep assumptions separate from mechanics: every parameter lives in `assumptions/`, never in code | Replicability requirement |
| Every number shown to a user is generated by the engine and carries its formula, sources, and assumption ids; nothing is typed by hand | Screens and documents must always agree |
| Everything in this repository is original work written for this Challenge | Official Rules, originality clause |

## Scope the tool must meet

- At least one entire state, with results aggregated to the state level. Primary state: Pennsylvania. The method must also run for states with less complete data.
- Five-year horizon. Outcome measure: housing units authorized by building permits, defined and justified in the documentation.
- A baseline (current rules and economics) plus the benchmark reforms below.
- For each reform: the change against the baseline, what drives it, how sensitive it is to key inputs, and what the model cannot tell policymakers.

## Benchmark reforms

| # | Reform | Required assumptions |
|---|---|---|
| 1 | Accessory dwelling units | One ADU on parcels with an existing single-family building; detached and semi-detached ADUs of at least 600 sq ft allowed; no additional parking |
| 2 | Missing middle | 2–6 units on parcels currently restricted to single-family use; up to three storeys; setbacks and lot coverage may be assumed non-binding |
| 3 | Transit-oriented density | More height or floor area near major transit stops; define "major transit stop" and justify the distance threshold; parking may be assumed reduced |
| 4 | Parking reduction | Reduce or remove residential minimums; state what parking developers still build |
| 5 | Development fee reduction | 50% cut across all fee categories; assume fees total $50,000 per unit |

## Technical gates (pass/fail)

- Runs from the documented setup with no undocumented manual steps.
- Automated tests cover the core logic, pass on a clean checkout, and have a documented command.
- No committed credentials; secret scanning on with zero unresolved alerts.
- Dependabot and CodeQL enabled; no unaddressed critical or high findings.
- Approved licence file (Apache-2.0).
- Software bill of materials documented.
- Data fetched by an automated script; no large datasets in the repository.

## What the judges weigh

| Criterion | Weight |
|---|---|
| Transparency & Explainability | 30% |
| Replicability & Scalability | 25% |
| Usability | 20% |
| Methodological Soundness | 15% |
| Policy Insight & Interpretation | 10% |

## Commands

```
make setup     install dependencies and pinned browser libraries
make data      fetch sources and build the state data pack (STATE=PA)
make test      run the test suite on the built-in synthetic state
make verify    lint, tests, end-to-end checks, licence audit, secret scan, document-number check
make app       serve the tool locally
```

A task is finished only when `make verify` passes.

## Writing style

Plain language. Short sentences. Define every technical term once. State limits openly. Say "likely range", not "forecast".
